# 05 · 实现路线对比

## A. vendor + 补丁 fork（推荐）

做法：把 `@deepseek-ai/dsh-client-ui-workspace/lib/client.js` 原样 vendor 进本仓库，用一个小 patch 追加自定义分组代码；禁用 loader 行 `ui-workspace`，挂载本包。

- ✅ 原生 UX 完全可控：第四项菜单、拖入/拖出、右键菜单、折叠、水印都能按核心写法实现。
- ✅ 不动核心包文件、不污染全局，卸载即恢复。
- ⚠️ 232KB vendor + 每次 DSH 升级需重打补丁（提供 `scripts/vendor.mjs` + `patches/` + `verify.mjs` 把成本压到「跑脚本 → 看 diff」）。
- ⚠️ 与上游功能漂移：升级后上游新增功能需重 vendor 才能拿到。

**升级管线（P1 落地）**：`vendor.mjs` 从安装目录抓 pristine 并记 sha256 → `build.mjs` 应用 `patches/000*.patch` 生成 `lib/client.js` → `verify.mjs` 断言「pristine 未改 + patch 干净应用 + id/inject 声明正确」→ 失败即拒绝安装。

## B. store 过滤 + 合成工作区（无 fork）

做法：包装 `workspaces` 快照，把已归组会话从真实工作区 `sessionIds` 中摘掉，再追加合成分组；核心 UI 照常渲染。

- ✅ 代码量小，复用原生的折叠/搜索/排序。
- ❌ 合成工作区会泄进工作区选择器、新会话目标、重命名/删除入口（需要额外过滤，易炸）。
- ❌ 跨组拖拽仍然缺失（T4），只能靠 DOM 事件补，脆弱。
- ❌ 无法在「分组方式」菜单里加第四项（T2），只能用别处的开关，交互不统一。

## C. 自绘覆盖层（无 fork）

做法：隐藏核心列表（CSS），在侧栏区域内自绘一套分组列表 + 拖拽。

- ✅ 完全自控、零 vendor。
- ❌ 要重写行渲染、虚拟化、水印、右键菜单、搜索联动，等于另造一个会话浏览器；视觉与交互必然与原生有差。
- ❌ 依赖 DOM 结构（`data-row-key`）与样式类名，DSH 升级即坏。

## D. 上游贡献（长期）

推动 DSH 核心把 `groupBy` 改成可注册表（类似 slot），本插件退化为注册者。

- ✅ 最干净，长期零维护。
- ❌ 不可控、周期长；可作为 A 稳定后的并行议题（写 issue/PR 草案放 `docs/`）。

## 评估矩阵

| 维度 | A | B | C | D |
| --- | --- | --- | --- | --- |
| 原生保真度 | 高 | 中 | 低 | 高 |
| 实现量 | 中 | 小 | 大 | 未知 |
| 脆弱度（对 DOM/内部实现） | 中（版本钉死 + verify） | 高 | 高 | 无 |
| 升级成本 | 机械（脚本 + diff） | 中 | 高 | 无 |
| 交互统一（菜单第四项） | ✅ | ❌ | ❌ | ✅ |
| 推荐 | **是** | 否 | 否 | 长期 |

**建议**：A 落地，同时把 D 的诉求整理成 upstream 提案（`docs/11-upstream-proposal.md`，P4 后补）。
